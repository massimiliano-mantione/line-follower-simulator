# Speaker notes — Lesson 01: Embedding Wasmtime

**Branch** `ws/simulator/01-wasmtime` · **Slot** 0:30–0:50 (20 min) · **Live demo — nobody codes**

Why this is a demo and not an exercise: engine/store/linker plumbing is API
discovery, not understanding. Forty minutes of doc-hunting for a result they cannot
reason about. But it is only 99 lines, it contains one genuinely surprising trap, and
it is where the *sandboxing* story lives — so you type it, live, while they watch.

## 1. The contract first (5 min)

Open `wit/world.wit` and read it top-down. Do not read all 200 lines — read the
*shape*:

- `import devices` — what the host gives the robot: sensors, motors, sleeping.
- `import diagnostics` — logging and file writing.
- `export robot` — what the robot must provide: `setup()` returning a
  `configuration`, and `run()`.

Three things worth pausing on:

- **`device-value` is eight bytes.** Not a nice variant per sensor type — eight raw
  bytes, reinterpreted as 8×u8, or 4×u16, or 2×u32 depending on the operation. Say
  why: this is what a real device register looks like. We are deliberately imitating
  reading a peripheral over a bus, not offering a comfortable Rust API. The
  comfortable API is `blocking_api.rs`, which the *robot author* gets to build on top.
- **`device-operation` is one variant covering every device.** So the host has one
  choke point where simulated time is charged, instead of twelve.
- **`setup()` returns the robot's physical configuration** — axle width, wheel
  diameter, sensor spacing and height. The *robot binary describes its own body*, and
  the simulator builds the physics model from it. That is a nice inversion worth
  calling out; it is also why Lesson 04 can derive every collider dimension from
  config.

Mention, without dwelling: `bot/src/wasm_bindings.rs` is generated by `wit-bindgen`
and checked in (see the commented-out lines at the top of `bot/build.sh`). That is
why we are *not* editing the WIT today — except in the optional capstone, Lesson 12,
where adding a device back end-to-end is the whole point.

## 2. Now type it (12 min)

Build `run_robot_simulation` from nothing, narrating each line. The order matters —
each step motivates the next.

```rust
let mut engine_config = wasmtime::Config::new();
engine_config.consume_fuel(true);              // <- the entire workshop is here
let engine = wasmtime::Engine::new(&engine_config)?;
```

Stop on `consume_fuel(true)`. One line. It is why this project works.

```rust
let mut store = wasmtime::Store::new(
    &engine,
    BotHost::new(stepper, total_simulation_time, workdir_path, output_log),
);
```

The `Store` carries our host state. `BotHost<S>` is generic over
`SimulationStepper` — so at this point the code does not know whether it is driving
Bevy and Rapier or a 96-line mock. Point back at the whiteboard.

```rust
let component = wasmtime::component::Component::new(&engine, wasm_bytes)?;
let mut linker = wasmtime::component::Linker::new(&engine);
linker.define_unknown_imports_as_traps(&component)?;
```

**The sandbox beat.** The robot is an untrusted binary — at a competition it is
literally someone else's code. It gets no WASI, no filesystem, no clock, no network.
If it imports something we did not offer, the import is wired to a trap. The only
way out of the sandbox is the functions in `world.wit`, and every one of them is
metered.

Contrast with the obvious alternative out loud: if the robot were a Rust trait object
compiled into the simulator, one `loop {}` would hang the simulator, one panic would
take it down, and one `std::fs::remove_dir_all` would be a very bad day. Here a
runaway robot just runs out of fuel and traps.

```rust
LineFollowerRobot::add_to_linker::<_, HasSelf<_>>(&mut linker, |host| host)?;
```

Wires our host implementations in. `HasSelf` says "the host state *is* `BotHost`".

Then the trap. Type it wrong first, on purpose:

```rust
let robot = LineFollowerRobot::instantiate(&mut store, &component, &linker)?;
store.set_fuel(fuel_for_time_us(total_simulation_time))?;   // WRONG - too late
```

Ask what breaks. Two things, and both are good:

1. **Instantiation itself consumes fuel.** Running the component's initializers is
   executing WASM, which burns fuel. A store with no fuel *traps immediately*, so we
   cannot instantiate before granting a budget.
2. So the budget must be set **before** `instantiate` — and then **reset afterwards**,
   or the robot's constructor and memory setup silently eat into its 60 seconds of
   simulated race time.

The correct shape, which is what is on `00-base`:

```rust
store.set_fuel(fuel_for_time_us(total_simulation_time))?;
let robot = LineFollowerRobot::instantiate(&mut store, &component, &linker)?;
store.set_fuel(fuel_for_time_us(total_simulation_time))?;   // fresh budget for the race
robot.robot().call_run(&mut store)?;
```

This is the kind of bug you find once and never forget. Worth the three minutes.

Finish with `get_robot_configuration`: same shape, but note the two differences —
a 1 ms budget (reading a config struct should be nearly free), and
`MockStepper::new(100)` instead of the real simulator, because building the Bevy
world before knowing the robot's dimensions would be circular. **`setup()` runs
against a mock, `run()` runs against Bevy.**

## 3. Where the time comes from (3 min)

Do not explain the arithmetic — just show the two functions and the constant, and
hand it over:

```rust
const FUEL_UNIT_NS: u64 = 50;      // 20 MHz CPU: one instruction, 50 ns
pub fn fuel_for_time_us(time_us: TimeUs) -> u64
pub fn time_us_for_fuel(fuel: u64) -> TimeUs
```

"We have a budget denominated in instructions, and a robot that spends it. In the
next 45 minutes you are going to turn that into a clock. Open `lessons/02-fuel`."

## Notes to self

- Timebox hard. This block overruns easily because the WIT file is interesting and
  people ask about component-model details. Park anything about resources, async
  ABI, or `wasi:` worlds — offer to talk at the break.
- If asked "why not `epoch_deadline` / instruction counting in the host?": epoch
  interruption is wall-clock based and preemptive, which is exactly the
  nondeterminism we are eliminating. Fuel is deterministic and *accountable* — we can
  read the remaining balance at any moment, which is what makes it usable as a clock
  rather than just a watchdog.
- If asked about fuel accuracy: fuel counts WASM instructions, not host cycles, so it
  is a *model* of a CPU, not a measurement of one. That is a feature — it is stable
  across machines and across Wasmtime versions' codegen improvements. Say it is a
  20 MHz Cortex-M-ish budget and move on.
